# Case Manager contract (schema v1)

Case Manager is an opt-in copy of customer-visible check results. The global `CASE_MANAGER_ENABLED` gate and every workspace policy default off. There is no backfill. A signed-in workspace user can enable capture for future accepted checks and choose an integer TTL from 1 to 45 days. Bearer API keys can submit checks; they do not grant case-history access. The case is owned by the verified portal workspace ID, not by the API key ID. Every signed-in user of that workspace may read its cases, raw final response and recorded artifacts. The product owner approved this workspace-wide access model on 2026-10-30; the portal currently has no finer customer roles.

## What creates a case

One authenticated, accepted business submission creates one logical case. Its `case_id` is an opaque UUID. `accepted_at` is the admission timestamp. The first transaction ID and later replay transaction IDs form `attempt_ids`; a replay retains the original `case_id` and expiry. Failed authentication creates no tenant case. Authenticated method, validation, entitlement and capacity rejections are auditable attempts with `not_run` or `could_not_complete` as appropriate; they are not successful checks. Polls, callback retries, downloads, key rotation, report generation and Form child calls create no additional verification case.

A workspace-scoped hashed transaction index supports exact lookup from an API log's transaction ID. It is removed with the case, including its replay attempt IDs.
The signed-in portal can filter `/portal/api/cases` with `transaction_id=<UUID>`; this remains subject to the workspace, policy version, expiry, service, outcome and time filters.

## Schema, outcome and artifacts

`lib/case-manager-contract.mjs` exports schema version 1. The encrypted payload records workspace ID, service ID, acceptance and expiry, state, outcome and reason codes, attempt IDs, final HTTP status and content type, the exact final customer-visible response, and internal artifact references. A `202` receipt is an attempt, not a final result. Pending cases become `complete` only after the saved final response is captured. Capture failure leaves `incomplete` with a sanitized error code and an alert. No repair path can rerun a supplier or AI call.

The outcome vocabulary is `pending`, `passed`, `failed`, `review_required`, `extracted`, `analyzed`, `not_run`, `could_not_complete`, and `unclassified`. The separate API request-status filter uses the final HTTP code; HTTP 2xx does not imply a business `passed`. The internal `passed` value for completed, eligible adverse-media and merchant screenings is shown as **No material findings**. It means no material findings within completed screening coverage, not legal or credit clearance. Entity-search `passed` is shown as **No candidates found** within the completed checks in that response; it does not certify all underlying sources. OCR completion means `extracted`, never identity verification. BSA completion means `analyzed`, never credit approval. Unknown dynamic integrations are `unclassified`. The overview highlights bounded service-specific fields and preserves returned values verbatim. Every response field, including nested arrays and unknown future fields, remains available in the separate formatted JSON view. Non-JSON supplier bodies stay text, never fabricated JSON. One-time callback secrets, credentials, and private configuration are removed before storage; uploaded document binaries are not duplicated.

These mapping rules use the repository's documented response contracts and synthetic fixtures. They are not authorization to enable customer workspaces. The dashboard shows service-specific summary cards and a bounded generic fallback for future integrations. The separate raw-response view retains every response field.

Artifact references contain internal owner and report IDs, stored only in the encrypted payload. A case PDF endpoint first authorizes the signed-in workspace and unexpired case, then uses its recorded original owner to fetch the private artifact. It must never authorize through a public-report lookup or a caller-supplied owner ID. Existing public capability URLs remain independently accessible.
OCR final responses retain their original five-minute signed artifact URLs as result fields; those links expire independently of the case. The case-scoped artifact endpoint remains available until case expiry.

## Retention and failure boundaries

The product owner approved explicit customer-facing wording about separate source copies on 2026-10-30. The account and case pages state the current adverse-media, OCR, BSA and public-PDF retention boundaries; the selected TTL only governs the Case Manager copy.

Case Manager TTL starts at `accepted_at`; OCR and OCR-containing Forms use `min(workspace TTL, 30 days)`. Reads reject a case at `expires_at` even when physical purge is late. Shortening TTL or opting out raises a monotonic visibility floor, so later re-enablement cannot resurrect old cases. A dedicated retirement message schedules early deletion. The expiry-index purge job runs every 15 minutes and targets physical deletion within 24 hours of expiry or opt-out, as approved on 2026-10-30; this remains a live QA gate, not a measured guarantee. Hitting its per-run cap or a storage error alerts operations. Deletion counts contain no PII. An expiry during pending processing prevents later capture from making the case readable.

Before a settings update raises the visibility floor, the API writes a durable due task in the dedicated Case Manager Table `retirement` partition. If that write fails, the policy update is rejected. The reconciliation job queries only the first four due tasks in that partition and advances each task with an atomic create/delete Table transaction when deletion needs another page; it never scans the shared usage table. A failed policy update leaves a harmless task that is retried briefly and then discarded. Queue scheduling accelerates retirement, while the due task recovers deletion if scheduling, delivery or dead-letter replay fails. Dead letters keep only the workspace, version, cursor and attempt needed for replay; they contain no case response or document data. A settings response with `retirement_recovery_pending: true` means visibility has stopped and the due task must still finish physical deletion.

The scheduled reconciliation job runs every two minutes and drains up to 16 batches of 32 messages (512 per run) within a ten-minute run budget. Each run logs received-message age p95/p99/max, elapsed time, and counts of received batches, processed messages, errors, and remaining retirement work. The nominal 256 messages per minute capacity exceeds the provisional 180 QPM synthetic test rate, but Azure-backed queue age, capture latency, and purge lag remain release gates.

This TTL governs only the Case Manager copy. Adverse-media JSON has its own 365-day retention. OCR source data has its own 30-day retention. BSA source retention is separate and does not yet have a final deletion schedule. Some PDFs are permanent and have public capability URLs; Case Manager TTL does not revoke those URLs. Disabling Case Manager does not change these source stores or existing service behavior.

No names, document text, credentials, full responses or signed URLs belong in Table indexes, queues, logs or alerts. The payload is application-encrypted with a versioned key and stored in a private dedicated UAE North Blob account. Filters use workspace-scoped indexed date, service and outcome metadata. Errors in indexing, encryption or final capture are sanitized and auditable. Global feature off makes no Case Manager storage calls and leaves API responses, billing, callbacks and supplier-call counts unchanged.

The product owner requires private network access before any Case Manager QA. The old production Container Apps environment has no VNet attachment; its network type cannot be changed after creation. On 2026-10-30 the separate VNet-integrated KYCProbe environment, private Blob/Table/Queue endpoints, linked private DNS zones and public-network-disabled Case Manager storage were provisioned. The manual probe job verified private DNS and managed-identity Blob/Table/Queue operations from a running container. The API deployment workflow still rejects direct Case Manager platform provisioning and requires a recent successful private probe, approved endpoints, disabled public storage access and the new environment before production capture or maintenance can be enabled. `parallelDeployment=true` now runs the new internal API and screenshot app with shared queue consumers off; `parallelCaseManagerQa=true` enables Case Manager against separately named QA metadata, Blob and queue resources and maintenance jobs in that internal environment. The manual `api-case-manager-qa-job.bicep` job tests authenticated routes, real Azure case and artifact storage, isolated synthetic OCR/BSA reconciliation, physical purge and queue-failure retirement using disposable workspaces. See [the private-network inventory and cutover runbook](case-manager-private-network.md). Customer QA and `CASE_MANAGER_DESIRED_ENABLED=true` remain gated on the full release evidence.

Before enabling capture for a disposable QA workspace, set the deployment environment's `CASE_MANAGER_MAINTENANCE_ENABLED=true`. After the release gates are approved, set `CASE_MANAGER_DESIRED_ENABLED=true`; routine and manual deployments both read this persistent desired state. `CASE_MANAGER_EMERGENCY_OFF=true` stops capture while retaining maintenance, and stays effective across subsequent deployments until cleared. The deployment refuses an enabled desired state without maintenance. Keep maintenance on during any capture rollback and do not remove the dedicated storage account.
