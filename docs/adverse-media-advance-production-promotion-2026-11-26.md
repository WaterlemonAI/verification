## Why this source is not yet a production activation

1. PR #157 is draft and stacked on `codex/gdelt-versioned-summary`, not `main`. Its hosted check passed, but it is neither reviewed nor merged. The repository workflow builds and deploys on a push to `main`; its configured `ai7uae-api` environment currently targets `ca-ai7uae-api-private-qa`, while the customer API is `ca-ai7uae-api`. No reviewed promotion path to the customer app has been demonstrated for this candidate.
2. The candidate's one-call JSON/PDF report is `POST /internal/adverse-media-advance/report-test`, gated by `ADVERSE_MEDIA_JEV_API_ENABLED` and an internal bearer token. The customer `/service/adverse_media_advance` route still queues the existing Advance pipeline and uses its older classifier and report finalizer. Turning on `ADVERSE_MEDIA_ADVANCE_ENABLED` would enable that older route, not the new Jev/Mistral report path.
3. The owner has authorized an interim JSON plus unsigned-PDF response while a trusted certificate is deferred. The internal report endpoint now has an explicit unsigned mode that marks the JSON and PDF accordingly. This mode is not yet wired into a customer route or deployment configuration. A future signed release needs the production Key Vault certificate/secret reference and trust chain.
4. Four recent QA reports were generated with the archive source explicitly unavailable to the local QA principal. The runtime managed identity can read the archive, but the exact candidate has not completed an archive-backed end-to-end run under that identity. The last cohort had zero adverse incident groups, so it did not exercise a live Mistral incident-summary call.
5. Per-policy adjudication is `not_run` in this candidate. Existing Advance entitlements, idempotent admission, polling, callback, cost accounting, persisted evidence, and report retrieval cannot be replaced by the synchronous internal test route without a reviewed compatibility and migration design.

## Safe promotion sequence

1. Finish a versioned customer contract for the new engine. Keep the existing `/service/adverse_media_advance` 202/callback route untouched. A new submission route must use customer API authentication, the existing Advance entitlement and rate, durable idempotent admission, a queue, and a polling result route. A worker must run the Jev/incident/Mistral engine, checkpoint costly stages, persist JSON and a private unsigned PDF, and settle or refund billing. It must not depend on a long synchronous HTTP request. Keep the new feature flag off until this is tested. Do not turn on `ADVERSE_MEDIA_ADVANCE_ENABLED`: that currently enables the older Gemini-based route.
2. Add an explicit production-target promotion workflow. The existing `deploy-api.yml` always builds on reviewed `main` and currently deploys to the private QA Container App through the `ai7uae-api` environment variable. Production promotion should accept the immutable image digest emitted by the successful QA deployment, verify its source SHA and artifact evidence, run an infrastructure preview against `ca-ai7uae-api`, then deploy that **same digest** behind the new flag with a recorded rollback digest. Never retarget the QA environment variable temporarily or rebuild a feature branch for production.
3. Review and merge PR #156, rebase and review PR #157 plus the customer-route and promotion changes, then let the main workflow build and deploy the digest to private QA. In its admin integration panel, set `adverse-media-jev` and `adverse-media-summary`; verify the Brave, Event Registry, archive, queue, and report-storage dependencies under the runtime identity.
4. From private QA, run at least one archive-backed adverse incident case, one no-adverse case, one provider failure, and an idempotent replay. Verify the public JSON contains no internal provider names, `report.digitally_signed` is `false`, the PDF visibly says unsigned, the PDF and JSON can be retrieved, and billing occurs once only on a completed check.
5. Promote the QA digest to `ca-ai7uae-api` through the reviewed production workflow with the new customer flag off. Read back the exact image, revision, configuration names, and traffic. Configure the same provider credentials in the production admin integration panel, enable the new flag, make an authenticated synthetic request, and verify polling, PDF retrieval, metering, and rollback. Only then mark the API live.
