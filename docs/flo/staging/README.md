# Flo staging deployment and runbook

This workflow is only for a separate non-production environment. For the existing live KYCProbe app, use [Flo live rollout](../live-rollout/README.md) and the production API workflow.

The staging workflow deploys a **reviewed commit** to a separate resource group and Container Apps environment. It never invokes the production deployment workflow. `parallelDeployment` is false so staging has OCR workers and custom domains; the names, storage accounts, identities, vault, certificates and API/buyer/Flo hosts must all be staging resources. The workflow enables the Flo runtime, but does not publish a template or assign a workspace.

## Before dispatch

1. Commit and review the Flo implementation and this staging workflow, then merge the reviewed commit to `main`. Enter its full 40-character SHA when dispatching [Deploy Flo staging](../../../.github/workflows/deploy-flo-staging.yml); the workflow rejects a SHA outside `origin/main`. Protect the `flo-staging` GitHub environment with the intended deployment reviewers and a staging-only OIDC identity. Configure its `STAGING_AZURE_CLIENT_ID`, `STAGING_AZURE_TENANT_ID`, `STAGING_AZURE_SUBSCRIPTION_ID` and `STAGING_ACR_NAME` variables.
2. Provision the separate staging resource group, Container Apps environment, runtime and worker identities, Log Analytics workspace, Key Vault, storage accounts, OCR and Ejari dependencies, provider credentials, and three managed certificates. Configure `api-staging.ai7uae.com`, `app-staging.kycprobe.com` and `flo-staging.ai7uae.com` or equivalent `-staging` hosts in DNS and TLS. The storage accounts must deny public network access and shared-key access; Flo and OCR need approved private Blob, Table and Queue paths plus managed-identity data roles.
3. Populate every `STAGING_*` variable read by [the parameter validator](../../../scripts/prepare-flo-staging.mjs). Resource names must include `stg` or `staging`; Flo, OCR, Ejari and bank-statement storage must be distinct, and Flo storage cannot be shared with any other configured account. Set `STAGING_FLO_STORAGE_NAME` to the staging account that will receive the existing Flo child-resource template. Set the four worker image variables to reviewed ACR `@sha256:` references; the workflow builds the API image from the selected commit and pins its digest itself. The configured ACR must also contain the pinned ClamAV image referenced by `api.bicep`. Use a staging alert mailbox. The validator rejects production hosts, non-staging resource IDs, shared Flo storage and mutable image tags.
4. Put staging-only values under the expected Key Vault secret names: `flo-data-key-v1`, `flo-session-hash-key-v1`, `flo-callback-signing-key-v1`, `flo-gemini-api-key`, `platform-smtp-password`, `document-ocr-data-key`, `document-ocr-download-key`, `ejari-data-key-v1` and `bsa-data-key`. Verify ClamAV, Gemini, OCR, provider and SMTP credentials before uploading controlled documents. The workflow references secrets by vault URI; it does not create or print them.

## Deployment behavior

The workflow checks out the supplied SHA, runs the repository tests and Flo desktop/mobile smoke, verifies the staging resource names and private storage settings, builds Bicep, pushes the reviewed API image, resolves its registry digest, then runs `what-if` on both staging Flo child storage and the staging API. The private-storage gate joins approved storage connections to their private endpoints and requires approved Blob, Table and Queue groups for the same storage account; three connections to one group do not pass. It applies those templates to **only** `STAGING_RESOURCE_GROUP` and probes the three staging hosts. Billing-notification scheduling, generic Case Manager capture and adverse-media background workers remain off in this stage deployment. The production template defaults are unchanged.

The workflow does not provision the prerequisite environment, identities, private endpoints, Key Vault, certificates, DNS or provider accounts. A failed preflight means those resources still need setup; do not substitute production IDs to make the run pass. Keep the generated `/tmp/flo-staging.parameters.json` inside the runner; it contains resource identifiers and public origins but no secret values.

## Controlled end-to-end run

After deployment, publish `supplier-onboarding-v1` in the **staging** admin console, assign Flo to a staging test workspace, set its price, enable its per-workspace configuration and callback, and verify staging-only mail delivery. Create a link from the staging buyer module. Complete all five supplier steps in a real browser with controlled trade licence, identity, premises and bank evidence; the legal-entity path also needs the supplied trade licence and premises documents. Inspect extraction, every check's actual response or explicit `not_run`, the versioned HTML/PDF/JSON report and the buyer Case Manager. Make a buyer decision and verify signed callback delivery and its staging document/report URLs. Retain the run ID, commit SHA, image digest, infrastructure `what-if`, case ID, provider coverage, callback receipt and any failed gates as release evidence.

This runbook does not claim that staging resources exist or that a live provider journey has passed. The new flow remains unpublished and unassigned until the controlled staging run is deliberately started.
