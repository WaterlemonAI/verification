# Flo live rollout on the existing KYCProbe app

Use the [production API workflow](../../../.github/workflows/deploy-api.yml) and its `ai7uae-api` GitHub environment. The [separate staging workflow](../../../.github/workflows/deploy-flo-staging.yml) is not part of this live-app path. No new staging resource group or staging credentials are needed.

1. Review and merge [Flo PR #131](https://github.com/WaterlemonAI/verification/pull/131). Keep `FLO_ENABLED` false during the merge deployment.
2. Dispatch the production API workflow with `provisionFloPlatform=true` while `FLO_ENABLED` is still false. It checks private storage and the runtime identity's Blob/Table/Queue roles, runs Bicep `what-if`, then creates the `flo-evidence` container, `FloCases` table and three Flo queues in the existing private storage account. This manual dispatch also redeploys the production API with Flo off. Do not run it against a staging account.
3. In the existing production API Key Vault, create and verify four distinct secrets: `flo-data-key-v1` (64 hexadecimal characters), `flo-session-hash-key-v1` (64 hexadecimal characters), `flo-callback-signing-key-v1` (64 hexadecimal characters), and `flo-gemini-api-key`. Verify the runtime identity can read them. Refresh the private storage data-plane probe, verify the pinned ClamAV image and upload scanner, configure `flo.ai7uae.com` DNS/TLS and set `FLO_CERTIFICATE_RESOURCE_ID` in the `ai7uae-api` environment.
4. Set `FLO_ENABLED=true` in that same production GitHub environment and dispatch the production API workflow. Its Flo preflight rejects parallel deployment, missing child resources or secrets, a stale private-path probe, a certificate outside the production Container Apps environment, and a missing pinned ClamAV image. It then deploys the digest-pinned API with Flo on. Changing a GitHub variable alone does not start a workflow run.
5. Publish `supplier-onboarding-v1` and enable it only for one controlled workspace. Set Flo pricing and callback, then create a supplier link through the buyer module. Complete the four-step supplier journey with controlled trade licence, identity, bank and premises evidence. Inspect extraction, each provider result or explicit `not_run`, the buyer case, versioned HTML/PDF/JSON report, buyer decision and signed callback.
6. Before enabling workflow self-service, verify a platform assignment, organisation copy and publish, unique link, applicant submission, buyer Restart, resubmission under the same application ID, decision, per-revision report, signed callback, applicant email, SMTP sender-domain records and Case Manager buckets. The workflow platform code is in review and has not been deployed by this guide.

The live legal-entity test still needs the supplied trade licence and premises documents. As checked on 2026-11-09, the existing storage account had private Blob/Table/Queue endpoints and the API runtime identity had all three data roles; the four Flo secrets were absent from the production API Key Vault. Those observations are read-only and must be rechecked at rollout time. Neither this runbook nor PR #131 deploys or enables Flo by itself.
