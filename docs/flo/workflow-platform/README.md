# Flo workflow platform: file-by-file implementation plan

The [no-code builder guide and release checklist](no-code-builder-upgrade.md) covers the visual editor, generated JSON, shared supplier preview and QA gates. Its source is implemented for review in this branch; it has not been deployed.

**Status (10 November 2026):** the new workflow platform is implemented in the Flo worktree for review, not deployed or enabled. The existing code-owned Flo service is live. This document remains the design and release checklist. The implementation adds the validated JSON schema and approved check catalog; immutable published versions and workspace-owned copies; platform and organisation management screens; a fixed supplier renderer; revision-preserving Restart; per-flow branding, callback and email configuration; and buyer application buckets. Existing code-owned KYS and Supplier Onboarding v1 versions remain supported.

The new routes are described in [`api/flo-openapi.json`](../../../api/flo-openapi.json). The main implementation is in `lib/flows/template-schema.mjs`, `checks-catalog.mjs`, `workflow-service.mjs`, `store.mjs`, `routes.mjs`, `processor.mjs`, `notifications.mjs`, `callback.mjs`, and the fixed `flow-site/renderer/` bundle. The platform screen is in `admin-site/`; organisation workflows and Case Manager are in `api-site/`. The `test/flo-*.test.mjs` suite and `scripts/smoke-flo-ui.mjs` cover the source behavior.

**Release gates:** the existing production Flo service currently uses `FLO_ENABLED=true`. At the user's direction, the workflow platform now defaults on when Flo is enabled; set `FLO_WORKFLOW_PLATFORM_ENABLED=false` to pause new workflow management and links. Follow the [production readiness file map](production-readiness-file-map.md). Verify private storage, Key Vault secrets, Flo DNS/TLS, upload scanning, provider access, SMTP sender-domain records, and callback delivery in the target environment. Run the complete platform-assignment → organisation-copy → publish → link → applicant → buyer Restart → resubmit → decision journey with controlled documents. Provider checks without a documented adapter or available evidence remain explicitly `not_run`; source implementation and mocked tests do not establish a live provider success result.

**Baseline:** `WaterlemonAI/verification` `origin/main` at `428c8f56dc5a5f15da11fc548823c0cf6b873da8` (10 November 2026, Dubai). Recheck the file map against `main` before implementation. This plan supersedes the code-owned-template assumptions in the older [Flo Option 1 guide](../README.md) for *new* workflows. Existing `kys-v1` and `supplier-onboarding-v1` cases must remain readable.

## Product decisions and invariants

- Platform and organisation admins edit a **validated JSON workflow schema** through the visual Builder, supplier-matched Preview and optional advanced JSON tab. Neither role uploads executable HTML or JavaScript. The schema can describe stages, conditional fields, document slots, declarations, approved checks, report sections and presentation tokens.
- Platform admins select checks from an approved, versioned catalog. An organisation admin may copy an assigned workflow, edit its schema and publish the copy directly for its own organisation. A copy receives a new globally unique `flow_id`, an immutable owner workspace, and `source_flow_id` lineage. It cannot be enabled for another organisation by its owner.
- A mutable draft is never used for a live application. Every publish creates an immutable version and definition hash; an application pins both at creation. Editing an active workflow creates a new draft and version. Old versions, original documents, reports and case events remain accessible without automatic Flo expiry.
- Global template and local workflow lifecycle states are `draft`, `active`, `paused`, `archived`. Pause stops **new links** while existing applications and buyer decisions continue. Archive removes the workflow from creation lists but leaves its cases, reports and audit history accessible. A platform pause overrides a local active state.
- A Restart is a buyer action before a final decision. It keeps the `application_id`, increments `application_revision`, records the buyer's required changes, and issues a new one-time link to the original applicant. The case stays in Restarted while the revision is being edited; resubmission moves it to Processing/Review. Accept and Reject are terminal for this release.
- Applicant emails go to the original link recipient. Decision and Restart emails should contain the status, reference and secure link where needed, not sensitive documents. Signed callbacks include the decision, revision, structured application snapshot and authenticated document/report references.
- Buyer decisions are durable before notification work starts. Callback or email failure must be visible and retryable, and must not reverse a case decision. Keep supplier projections minimal; never send buyer-only checks or SMTP credentials to the supplier browser.
- Keep AI7EDD as the public review label in the buyer UI, reports and API projections. Provider model names and credentials stay internal, and the applicant journey ends at a receipt without exposing verification review.

### Identity and bucket rules

Keep `flow_id` as the public immutable workflow ID used by routes. Add `source_flow_id`, `owner_workspace_id` (`null` for platform templates), `schema_version`, `published_version`, `definition_hash` and lifecycle state. Display a separate editable `name`; do not encode a mutable name in the ID. Existing flow IDs remain valid.

Derive the application's primary bucket from **case state plus explicit buyer Restart and link-delivery metadata**, rather than from a label in the UI:

| Bucket | Rule |
|---|---|
| Open | One-time link exists and has not been redeemed. Show `sent`, `failed`, `not_attempted` or `manually_shared` as a separate delivery badge; `link_issued` alone is not proof that email was sent. |
| In progress | Applicant opened the initial link and has not submitted. |
| Processing / Review | Submitted or processing, or ready for a buyer decision. Include provider failures as visible review findings. |
| Restarted | Buyer explicitly requested Restart and the new revision has not been resubmitted. An automated `needs_correction` finding alone does not put a case here. |
| Accepted / Rejected | Terminal buyer decision. |
| Expired / Failed | Expired unused link or processing failure; keep accessible and actionable outside the four requested buckets. |

### Route contract to finalise before coding the screens

| Actor | Proposed routes | Required behavior |
|---|---|---|
| Platform admin | `GET/POST /admin/api/flows`; `GET/PATCH /admin/api/flows/{flowId}/draft`; `POST /admin/api/flows/{flowId}/copy`, `/publish`, `/lifecycle`; `GET/PUT /admin/api/flows/{flowId}/assignments` | Admin session and CSRF on writes; draft and publish use expected version/ETag; list includes lifecycle and active-organisation count. |

## Release order and ownership

1. Steps 1–2 are the **platform foundation**. Keep organisation self-service hidden behind a feature flag until the schema, storage and authorization tests pass.
2. Step 3 enables template and workflow authoring in staging. A platform-owned template must be assigned before the organisation can copy it; an organisation-owned copy is available only to its owner.
3. Steps 4–5 complete revisioned decisions and reliable notifications. The existing buyer decision path remains available for old pinned cases throughout migration.
4. Step 6 exposes buckets and turns on self-service for a controlled workspace, then broader workspaces only after live pilot evidence is reviewed. The planned staging journey remains a separate unverified QA gate.

The existing `flo` module entitlement and charge remain the admission gate. Before charging organisation-owned copies, explicitly test the inherited price and idempotency policy; do not let a new flow ID bypass a workspace's Flo assignment or create an unpriced application.
